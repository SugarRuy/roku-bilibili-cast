## 找到并修正的问题

这些问题通过代码检查与确定顺序的延迟响应测试复现；
没有声称它们都在上述 42 秒现场采样中发生。

1. **视频详情、播放地址和相关推荐缺少统一的请求归属检查。**
   先选择 A 再选择 B，A 的迟到详情可以启动 A；
   换视频查详情期间，旧画质／播放地址响应也可能重新启动旧流。
   旧推荐还能覆盖当前推荐。现在先取消并立即清空旧任务引用，
   回调必须匹配当前任务节点，完成后清空引用，拒绝重复完成通知。
   HTTP 取消仍由 Task 线程执行，没有从渲染线程强制 STOP 网络 Task。

2. **切视频残留旧画质与暂停恢复状态。**
   清理待切画质、恢复位置／备份和“启动后暂停”标记。
   新视频详情尚未确定或查询失败时，修改画质只保存偏好，
   不会用旧视频标识重新请求播放。旧解码器的 error／finished 通知
   也不能在查新视频时触发旧视频降级重试或自动连播。
   已退出的播放器不能因排队的操作再次启动后台请求。

3. **互动状态的迟到结果可能抢回焦点。**
   状态查询替换时取消前一个；关闭设置或打开评论时取消状态查询。
   结果只在当前播放器、当前请求和仍打开的设置侧栏中显示。
   操作失败可以提示原因，但不能重新打开已经关闭的菜单；
   关闭侧栏后不再发起静默状态刷新。

4. **互动操作尚未完成时可以再次提交。**
   待处理操作存在时拒绝第二次提交并提示等待。
   回调只处理当前操作一次。测试中的投币、失败与迟到返回均是模拟数据，
   没有调用账号写接口或消耗硬币。客户端取消请求并不保证撤回已经
   到达服务器的操作；此修复没有加入自动重试或自动投币。
